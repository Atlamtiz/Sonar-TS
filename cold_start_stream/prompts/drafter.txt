# WHAT A GOOD SKILL CONTAINS

A skill teaches a METHOD for a kind of question. It is read for questions you
have never seen, on data you have never seen.

- Every quantity the question states — which channel, which period, how many
  results, which threshold, which window length, which pattern and in what
  order — is READ FROM THE QUESTION. Write it as a placeholder (<channel>,
  <start>, <end>, <k>, <threshold>, <n_days>, <pattern>) and tell the generator
  to fill it from the question. Never hard-code a value that a question supplies.
- Never state facts about a particular data set: no channel ids, no years or
  dates, no "the answer is usually …", no sizes, counts or positions that you
  inferred from examples. Method constants that are part of the algorithm (a
  smoothing span expressed relative to the series length, a quantile used as a
  robust threshold, a minimum number of cycles) are fine, and must be justified
  in one clause.
- USE THE SYMBOLIC INDEX FOR QUESTIONS ABOUT FORM. When the questions describe
  the form of ONE curve — a rise, fall, flat stretch, peak, dip, plateau, step, a
  sequence of trends, calm vs. volatile stretches — the algorithm MUST begin with
  an index search and the snippet MUST contain it (a pattern search on the
  symbolic column of a feature table, as the INDEX GUIDE's codebook shows). Say
  which feature table: the one whose token length fits the DURATION OF THE SHAPE
  (a shape inside a day -> daily_feature), never the span of the question's time
  range — write this rule down explicitly, the generator gets it wrong otherwise. Give the GENERAL rule that turns the words of a question into a
  pattern: symbol classes, run lengths counted in tokens, parts joined in the
  order the question gives. Put into the pattern exactly what the codebook says
  the symbols express — no more (a property the symbols cannot express is
  measured on raw_data in the verify step) and no less (a property they do
  express belongs in the search). Add slope / std_val / min_val / max_val filters
  where they help. Keep the pattern loose. Then verify and rank on raw_data, for
  the shortlisted windows only, and fall back when the shortlist is empty or
  shorter than the number of results asked for. A skill for such questions that
  scans all of raw_data and never touches the index is NOT acceptable: it is slow
  (time limit) and it ignores the one structure that was built for these
  questions. The INDEX GUIDE above is always visible to the code generator, so
  do not repeat it — add what it does not say: the pattern rule and the
  verification for THIS kind of question. For questions that are NOT about form
  do not force an index search; use whichever index columns help (min_val /
  max_val / avg_val / std_val / slope), or raw_data directly for a plain
  aggregate.
- RANKED-LIST answers (top-k days, best window) need an explicit RANKING KEY: the
  quantity, and the part of the window it is measured on (the segment the
  question names, not the whole day). Take it from the diagnosis's ranking_key
  when one is given, compute it on raw data, and state how ties are broken.
  Finding the right windows and ranking them by the wrong quantity scores zero.
- Include ONE runnable Python snippet that uses `conn`, `pd`, `np`, contains the
  placeholders above, and ENDS with `_result = …` in the shape the eval_metric
  requires. Keep it under 60 lines. Assign every placeholder on its own line
  (`CH = "<channel>"`), never by tuple unpacking — a generator that fills three of
  four placeholders would crash on `A, B, C, D = …`.
- State the boundary conditions that broke earlier attempts (empty candidate
  set, inclusive/exclusive ends, sampling step, ties in ranking, NaNs).
- Use what the database actually offers. The section "TABLES AND COLUMNS" below
  shows a real task database; if it has a column or table that the question's
  wording points to, the method should use it.
- Learn from the REFERENCE SOLUTIONS when some are given: they are code that
  answered similar questions correctly. Take their method, not their literal
  values.
- LENGTH. The whole document stays under about 900 words of prose plus ONE code
  snippet of at most 80 lines. In PATCH mode REWRITE the document as a whole:
  fold the fix into the algorithm and delete what it supersedes. Never append a
  new section or a new special case per fix — a skill that grows with every
  patch ends up cut off and useless.
- SELF-CONTAINED. Never refer to another skill by name or id.
- The code fence must be closed and the snippet must be syntactically valid
  Python once placeholders are filled.
